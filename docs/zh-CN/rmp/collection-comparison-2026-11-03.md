**为什么慢脚本耗时更长**

| 实现           | `collect_rmp_osu.py`                              | `osu_rmp_sync.py`                                  |
| -------------- | ------------------------------------------------- | -------------------------------------------------- |
| 接口           | 自行构造 RMP GraphQL                              | 通过 `ratemyprofessors-client==3.0.2` 调用 GraphQL |
| 教授名单每页   | 默认 100                                          | 固定 50                                            |
| 评论每页       | 默认每位教授 100 条                               | 固定每位教授 20 条                                 |
| 一次 HTTP 请求 | 默认合并 10 位教授的评论分页，参数最多 20 位      | 一位教授的一页评论                                 |
| 请求间隔       | 至少 10 秒                                        | 默认随机 3–4 秒；README 示例为 3–5 秒              |
| 并发           | 串行                                              | 串行                                               |
| 评论恢复       | 持久化每位教授的分页游标                          | 未完成教授下次从第一页重抓，用指纹去重             |
| 网络恢复       | 最多 5 次尝试，部分错误退避，429 尊重 Retry-After | 客户端重试配置为 0；部分错误留待下次运行           |
| 持久化         | PostgreSQL，结构化字段及原始 JSON                 | SQLite WAL，结构化基础列及模型 JSON                |

快脚本的优势是**用较少请求取得更多内容**。例如取 10 位教授各 20 条评论，快脚本可以一次请求完成，慢脚本需要 10 次；取 10 位教授各 100 条时，理论上可由 50 次分页请求缩减为一次合并请求。实际提升受教授评论分布、分页返回、网络和服务端限制影响，不能把理论请求倍率当成实测时间倍率。

以上为当前代码默认参数。导出的 run metadata 没有记录实际 `page_size`、`batch_size`，不能由现有导出精确重建那次运行所用参数或请求总数。

在 22:41 快照中，慢脚本还剩 **3,440 位有评分教授未完成评论同步**。按 PostgreSQL 已有的各教授实际评论数、每页 20 条计算，预计还需要约 **4,606 次请求**：Columbus 4,367 次、Lima 93 次、Mansfield 146 次。默认 3–4 秒间隔对应约 **3.84–5.12 小时**，按均值约 4.48 小时；网络、处理、失败重跑可能增加耗时。README 的 3–5 秒配置对应约 3.84–6.40 小时。它是固定快照下的估算，随采集推进而减少。

如果目的是独立客户端研究或比较接口行为，跑完有实验价值；如果目的是为 osu-eval 获取可用 RMP 数据，继续跑完的边际收益很低。

**数据细节：哪些真的更完整**

PostgreSQL 保存不可变的 RMP 评论 ID、完整时间文本、独立的 `helpful_rating` 和 `clarity_rating`、难度、再选意愿、线上课、学分、出勤、成绩、教材、标签、投票、教师回复和原始 JSON。教授详情还有课程列表及评分分布，更适合长期维护、去重、SQL 查询和重新建模。

SQLite 的 `payload` 是第三方客户端的 Pydantic 模型 JSON，不是原始 GraphQL 响应。它仍保留评论标签、投票和 `details` 中的出勤、学分、成绩、教材，因此不能说它只有正文；真正的损失包括：

- 接口请求了评论 `id`，但客户端解析时丢弃，模型没有 ID 字段。
- 评论日期只保留年月日，丢失时间与时区；客户端日期解析失败时会代入当天日期。
- `quality` 优先使用 `clarityRating`，无法同时保留独立的 helpful 分值。PG 全库有 **22,224 条**评论这两个分数不同。
- 评论再选意愿、线上课属性、教师回复、审核属性等没有保留在该 Rating 模型中。
- 教授 payload 虽有 `rating_distribution` 和 `tags` 键，本次 SQLite 数据中两者全部为空；同步代码没有额外请求教授详情来补全它们。

按 2026-11-03 截止日计算，PG 评论覆盖 2000-12-16 至 2026-11-03；近三年有 **17,536 条（16.70%）**，近一年有 **6,241 条（5.94%）**。大部分是历史评论，对当前选课的直接价值低于总行数给人的印象。应优先看“当前授课教师 + 当前课程 + 近几年”的有效覆盖，不把 9,392 位历史档案当作当前在职教师人数。

**需要先做的清洗与完整性判断**

1. 两库均有 1,182 位教授 `num_ratings=0`，对应的均分/难度 0 应当展示为暂无数据。`would_take_again_percent=-1` 或 SQLite `percent_take_again<0` 有 3,833 位，应转换为未知值。
2. PG `review.rating_tags` 实际有两种 JSON 类型：61,080 条是空数组，43,920 条是由 `--` 分隔的字符串。虽然列类型是 JSONB，不能直接假设所有值都是数组。应保留原值并生成规范化标签数组。
3. 出勤同时出现 `mandatory/non mandatory/Y/N/空串`，应归一为是/否/未知。教材是枚举/哨兵值，不能直接当布尔；PG 中非 NULL 有 90,391 条，其中 `-1` 有 12,077 条、`0` 有 13,166 条，需要明确枚举语义。成绩也有 `Not sure yet`、`Rather not say`、退课等值，不能简单按字母成绩统计，更不能用于成绩预测。
4. 课程原文存在 `HIS/HIST/HISTORY`、空格、连字符、纯数字、旧课程编号等情况；需要结合课程目录和院系证据映射，不能只删除标点就自动合并。
5. RMP `numRatings` 与实际可分页评论不是严格相等的口径。本次 PG 教授 `num_ratings` 合计 **104,216**，但实际评论为 105,000；798 位实际更多、35 位实际更少，8,559 位相同。不能仅凭这种差异判断脚本丢页。
6. 本次 PG 有较强的内部一致性证据：实际唯一评论数、`run_professor.reviews_loaded` 合计、`ratings_distribution.total` 合计均为 **105,000**；每位有分布教授的 distribution total 与 reviews_loaded 也一致；没有重复评论 ID 或孤立教授外键关系。它支持数据质量较好，但不能证明线上数据永远无遗漏，搜索名单仍有上述差异。

**代码维护建议**

快脚本更适合作为主采集器，建议优先修补以下边界后再安排长期更新：

- 搜索和评论分页都增加游标缺失、不前进、循环重复保护；当前两段循环没有这些保护。
- `num_ratings` 更新采用当前观测值，另存历史最大值（如确有需要）。当前 `GREATEST(新值,旧值)` 使它只能增加，无法反映删除。
- 把“成功遍历完成”“教授节点不存在”“详情异常”“评论数为零所以跳过详情”区分成状态；当前 `teacher=null` 也会直接标记完成。
- 用实际去重后评论数及分布总数记录校验结果，将预期数、返回数、存储数分别保存，不以单个计数决定完整性。
- 对删除、消失的教授、评论和校园关系增加观测/失活策略。目前主要是 UPSERT 和 last_seen，不会自动删除旧记录。
- 保存实际运行参数、请求总数、耗时与异常计数。现有元数据不足以解释每次运行的性能变化。
- 这套表主要保存最新/累计数据，run 表保留运行进度；它不是每轮教授和评论内容的不可变历史快照。需要研究编辑历史时，应另存版本或变化摘要。

慢脚本若继续维护，首要任务是保留 RMP review ID 和原始时间，避免内容指纹作为唯一主键；其次是持久化评论分页游标，记录实际同步条数。当前 `reviews_synced_count` 写入的是预期 `num_ratings`，不是实际抓到的 `seen`，容易让名字误导分析，并可能在异常情况下把不完整数据当作完成。名单页的空游标也同时表示未开始或已结束，难以作为完整的运行审计记录。

当前快脚本只有四项纯函数单元测试，涉及查询拼接、布尔值、Retry-After 和参数限制；没有对在线接口、数据库事务、异常分页或跨页完整性进行集成验证。本次分析未发起在线采集测试。

**对 osu-eval 项目的实际收益与顺序**

当前 `src` 中没有 RMP 数据读取；网站仍从 `osu_eval` 查询官方评价，按 `subject + catalog + campus` 对应课程，再通过 OSU 邮箱的 `name_dot_number` 精确识别教师。RMP 两库都没有这个官方教师标识，因此采集完成不会自动让网站获得这些内容。

最高价值的数据组合是：**RMP 稳定教授 ID + 校区 + 姓名/院系 + 课程证据 + 评论日期 + 正文 + 难度 + 样本量**。它可以补充官方评价较少覆盖的考试方式、作业负担、课堂要求和学习体验。

推荐依次推进：

1. 保留 PG 主数据及现有 SQLite，提取 SQLite 独有的 23 位教授档案和那一条未匹配评论，作为待核实补充；避免重新整库采集来获得这些已有内容。
2. 建立显式 `rmp_professor_id → osu_eval.instructor_id` 映射，保存姓名、院系、校区、课程证据和人工确认状态。仅凭同名自动合并存在误配风险；低置信度候选应保留为未确认。
3. 建立课程映射，先覆盖当前目录中确实开课、已有可靠教师映射的课程。先用近三年评论做课程内的难度与经验展示，并展示样本数和最新评论时间。
4. 分开呈现官方 SEI/SSLE 与 RMP，维持各自来源、样本和口径；不要直接混成一个总分。RMP 是自选样本，也没有官方评价的邀请人数和响应率，现有官方评分规则不能直接照搬。
5. 再做标签/主题归纳和定期更新。优先刷新当前授课教师及近期评论；定期全面校验编辑、删除和数量口径，避免仅靠评论数是否变化决定全部更新。

审核状态、`created_by_user`、lock 等字段主要用于来源与运维审计，业务优先级较低；本次 `created_by_user` 全部为 false，不适合据此判断评论者是否可信。

**停止与保存建议**

可以在原采集终端按一次 **Ctrl+C**，等待脚本输出 `DB saved` 并关闭连接。脚本按评论页提交，已提交内容会保留；不完整教授下次可以重新同步。不要在写入过程中只复制主 `.sqlite` 文件或直接删除 `-wal` / `-shm`。需要在线保存时使用 SQLite backup；正常关闭后再复制主库更容易操作。临时分析副本不能代替长期备份。
